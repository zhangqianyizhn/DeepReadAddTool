# Agent 自主发现并生成 RAG 工具：FinanceBench 阶段性实验报告

## 一、研究问题

本阶段不再只让高阶模型为 Student 改写一段通用提示词，而是提出更强的研究问题：

> Agent 能否只根据训练集上的失败轨迹，自主发现 RAG 系统的结构性瓶颈，提出一个新工具，写出可执行代码与调用策略，并通过开发集修复和冻结测试验证其泛化效果？

这里的关键不只是“让 AI 写 Python”，而是形成完整闭环：

```text
Student 运行训练题并记录检索轨迹
→ Analyzer 从失败中归纳可工具化机制
→ Repair Agent 生成 ToolSpec、工具代码、策略和测试
→ 静态安全检查与自生成测试
→ Dev 严格 A/B
→ 仅依据 Dev 反馈自主修复
→ 冻结工具与哈希
→ Test 只运行一次
```

## 二、为什么从提示词优化转向工具生成

### 2.1 全局提示词优化的结果

早期 Teacher-Student 实验在相同 141 题上，把 Teacher 生成的 `minimal_patch` 注入 Student：

| 指标 | Baseline | 优化提示词 | 变化 |
|---|---:|---:|---:|
| 归一化准确率 | 78.90% | 79.08% | +0.18 个百分点 |
| 平均输入 Token/题 | 273,536 | 307,339 | +12.36% |
| 平均耗时/题 | 45.9s | 50.1s | +9.00% |

22 题变好、22 题变差，净增仅 1 分。实验说明“一套面向所有题的自然语言注意事项”存在明显负迁移：例如扩大搜索可能修复漏检题，也可能给原本正确的题引入无关证据。

### 2.2 人工实现标题路由的正向结果

前期根据 bad case 人工实现 `search_document_titles` 后，FinanceBench 141 题严格 A/B 得到：

| 指标 | 同配置 Baseline | 人工标题实体路由 | 变化 |
|---|---:|---:|---:|
| 归一化准确率 | 78.55% | 85.11% | +6.56 个百分点 |
| 总得分 | 443 | 480 | +37 |
| Evidence Recall | 15.72% | 20.92% | +5.20 个百分点 |
| 输入 Token/题 | 245,020 | 116,556 | -52.43% |
| 耗时/题 | 137.8s | 84.4s | -38.71% |

这说明直接改变检索工作流，比要求模型“更仔细地核对文档”更可靠。但该工具包含人类分析、工程设计与数据集经验，不能回答“Agent 能否自己发现并生成工具”。因此本阶段重新设计了盲重建实验。

## 三、实验设计与防泄露约束

### 3.1 数据划分

FinanceBench 141 题被固定划分为：

- train：60 题，用于产生 Student 轨迹和 Agent 诊断；
- dev：20 题，用于选择与修复候选；
- test：61 题，只在工具冻结后运行一次。

### 3.2 盲重建约束

Analyzer 和 Repair Agent 在初始生成阶段不能读取：

- 已有 `search_document_titles` 源码；
- 人工标题路由报告；
- 人工错误类型标签；
- dev/test 答案与反馈。

Analyzer 只看到训练案例中的问题、Gold、Gold Evidence 来源、Baseline 答案、评分原因和原始检索轨迹。Repair Agent 根据 Analyzer 的诊断生成工具。

### 3.3 “完全由 AI 生成”的准确表述

最终冻结候选的 ToolSpec、算法代码、调用策略与第二轮修复内容均由 `deepseek-v4-flash` API 输出，最终代码 SHA-256 为：

```text
74dcab8e11db78721db730b74e53e7261ebf5e3e458e7ce4220d9d7c6b7edb03
```

该代码没有人工逐行改写。但实验仍然运行在人工定义的 harness 内：人类规定了 train/dev/test、可见信息、工具输入输出接口、安全检查和测试门槛。因此更严谨的说法是：

> 工具算法与代码在人工定义的实验框架内由 AI 自主生成和修复，而不是“完全没有人类设定”。

## 四、Agent 自主发现了什么

Analyzer 在 16 个训练失败和 4 个训练成功案例中，判断最频繁的结构性问题是：

> Agent 经常不是找不到内容，而是在 82 份报告中先进入错误公司或错误期间的文档，随后在错误范围内反复搜索并得出“没有找到”。

Analyzer 估计该机制出现在约 10/16 个失败案例中，因此提出 `document_inventory_search`。

该工具只读文档元数据，不读正文。它从问题和 `source_name` 中解析：

- 公司名称或缩写；
- 财年；
- 季度；
- 报告类型；
- 明确日期。

然后按加权匹配排序：公司匹配权重最高，其次为日期、年份、季度和报告类型。返回 Top-k 候选、匹配原因与覆盖统计，再让 Agent 把后续 BM25、正则和章节读取限制在候选 `doc_id` 内；没有强候选时仍允许全文回退。

这与人工标题工具属于同一类“先选文档，再搜正文”思想，但实现并不相同：AI 候选使用通用元数据解析、首字母缩写和前缀规则，没有复制人工工具中的 FinanceBench 公司别名表。

## 五、开发集自主修复

### 5.1 Round 1

| 方案 | Dev 准确率 | 平均分 | 输入 Token/题 | 耗时/题 | 胜/平/负 |
|---|---:|---:|---:|---:|---:|
| Baseline | 85.00% | 3.400 | 204,979 | 44.3s | — |
| AI 初始工具 | 88.75% | 3.550 | 104,744 | 38.5s | 1/19/0 |

初始工具已有正向信号，但仅提升 1 题。

### 5.2 Round 2

Repair Agent 只读取 Dev 反馈和轨迹，自主发现并修复：财年正则只取到世纪前缀、日期后缀污染公司名、日期正则 group 崩溃、possessive/multiword/initialism 匹配不足等问题。第二版自生成测试 9/9 通过。

| 方案 | Dev 准确率 | 平均分 | 输入 Token/题 | 耗时/题 | 胜/平/负 |
|---|---:|---:|---:|---:|---:|
| Baseline | 85.00% | 3.400 | 204,979 | 44.3s | — |
| AI 修复工具 | 92.50% | 3.700 | 98,887 | 33.1s | 2/18/0 |

Dev 上的净增为 6 分，因此按预先规则冻结工具并打开 test。

## 六、冻结 Test61 结果

| 方案 | 准确率 | 平均分 | 输入 Token/题 | 输出 Token/题 | 耗时/题 | Recall |
|---|---:|---:|---:|---:|---:|---:|
| Baseline | 90.98% | 3.639 | 480,710 | 3,934 | 55.3s | 31.97% |
| 冻结 AI 工具 | 90.98% | 3.639 | 240,003 | 3,202 | 35.9s | 27.32% |

最终成对结果为 1 胜、59 平、1 负，净分 0。

因此，冻结测试支持两条不同强度的结论：

1. **效率结论成立**：平均输入 Token 下降 50.07%，平均耗时下降 35.06%；
2. **准确率结论不成立**：没有测到 test 准确率提升，Dev 的 +7.5 个百分点没有泛化到 test。

## 七、为什么人工工具曾显著提分，而自主工具在 Test 上不提分

两次实验不能只看工具名称直接比较，因为存在三项重要差异：

1. 人工标题工具的 141 题结果是探索性全量 A/B，不是严格未见 test；自主工具使用 60/20/61 隔离；
2. 人工工具实验的 Student 更弱，Baseline 只有 78.55%，错误空间较大；新实验使用 `deepseek-v4-flash`，Test Baseline 已达 90.98%，61 题只有 7 题未满分；
3. 人工工具包含 FinanceBench 定制别名和人为工作流经验；AI 工具必须采用通用规则，且不能读取旧工具。

新工具并非没有工作。其文档路由 Top1 为 45/61，Top5 为 60/61；7 道最终未满分题均进入了正确公司报告。它主要消除了错误文档搜索和重复调用，因此显著节省成本。但剩余错误大多发生在路由之后：指标公式歧义、表格行选择、符号解释和停止策略。文档工具无法直接修复这些层级。

## 八、失败案例审计带来的新结论

冻结 Test 的 7 道未满分题可分为：

- 指标或公式口径歧义：3 题；
- Gold、Judge 与 Evidence 冲突或疑似标注问题：2 题；
- 数值符号推理：1 题；
- 派生指标缺失与搜索停止失控：1 题；
- 文档路由错误：0 题。

完整逐题日志与分析见 `FINANCEBENCH_TEST61_7_FAILURES.md`。

这意味着 FinanceBench 对“文档路由工具”已经挖掘得较充分。继续根据 Test61 错误生成新工具会把测试反馈泄露到算法中，也很难再检验 Agent 是否能在陌生数据结构上独立发现新能力。

## 九、当前研究结论

本阶段最准确的结论是：

> Agent 可以在不读取人工标题工具的情况下，从训练轨迹中自主归纳出“错误文档选择”这一结构性瓶颈，生成可执行的文档元数据路由工具，并通过自主修复获得显著的效率收益；但当前实验没有证明该工具能在严格 held-out FinanceBench test 上提高准确率。

这不是方向失败，也不能写成“AI 已经自动生成了一个普遍提分工具”。它证明了闭环中的前三件事：发现机制、生成代码、依据 Dev 自主修复；尚未证明的是跨样本、跨数据集的稳定质量提升。

## 十、下一步：更换数据集

### 10.1 首选 Qasper

本地已经有 `Data/Qasper/qasper-dev-v0.3.json`，不需要立刻向师兄索要新数据。Qasper 包含 5,049 个问题和 1,585 篇 NLP 论文；问题基于标题与摘要提出，答案位于论文全文，并带 supporting evidence。它适合验证 Agent 是否会从“公司/年份路由”之外发现论文场景的新工具，例如章节定位、表格/实验设置定位、跨段证据聚合或术语解析。数据集说明见 [Qasper 原论文（NAACL 2021）](https://aclanthology.org/2021.naacl-main.365/)。

为了防止同一论文的不同问题跨集合造成泄露，必须按“论文文档”划分 train/dev/test，而不是随机按问题划分。

Qasper 是公开数据集，不能完全排除基础模型在预训练阶段见过部分公开内容；这与“研究过程中把 test 反馈重新用于修复”是两种不同的泄露。前者可通过同一 Student 的严格成对 A/B、文档级集合隔离、Evidence Recall/证据定位等指标来降低影响并限制结论；后者必须通过冻结 test 和禁止反馈回流直接杜绝。已有 `server_results/Output/Qasper` 结果也不得输入 Analyzer 或 Repair Agent。

建议第一阶段规模：

- train：约 60 题；
- dev：约 20 题；
- test：约 50–100 题；
- 三组所对应的论文必须互不重叠；
- Agent 不能读取 FinanceBench 人工/AI 工具源码，只能使用通用的工具生成 harness；
- 最多允许两轮 Dev 修复，然后冻结并只运行一次 Test。

### 10.2 第二选择 HotpotQA

本地已有 `Data/HotpotQA/hotpot_qa_100.json` 和文章集合。HotpotQA 的问题要求跨多个 supporting documents 推理，并提供句子级 supporting facts，适合观察 Agent 是否自主提出实体链接、问题分解、跨文档 hop 或 supporting-fact coverage 工具。官方论文说明其包含 113k 个多跳问题，并要求多文档推理与证据支持：[HotpotQA 原论文（EMNLP 2018）](https://aclanthology.org/D18-1259/)。

但本地当前只有 100 题小集合，更适合作为 Qasper 之后的跨数据集复现实验，而不是立即用于多轮 train/dev/test 调参。

### 10.3 为什么不继续 FinanceBench

FinanceBench 已经产生：

- 多轮人工 failure analysis；
- 提示词优化结果；
- 人工标题工具；
- 60/20/61 自主工具闭环；
- Test61 逐题反馈。

继续使用它的边际价值主要是工程回归，而不是检验陌生环境下的自主工具发现。当前结果应按 `FINANCEBENCH_EXPERIMENT_FREEZE.md` 封存。

## 十一、下阶段要回答的核心问题

换到 Qasper 后，不应预先规定 Agent 必须生成哪一种工具。真正需要验证的是：

1. 在完全不同的文档结构中，Analyzer 是否仍能从失败轨迹提出可执行、可证伪的工具能力；
2. 生成工具是否通过 Dev，而不是只在训练失败上自洽；
3. 冻结工具是否在未见论文的 Test 上提升准确率、Evidence Recall 或效率；
4. FinanceBench 生成的 `document_inventory_search` 是否能直接迁移，还是 Agent 会生成全新的数据集特定工具；
5. 多工具竞争、回退和停止机制是否能避免某个工具在不适用题目上造成负迁移。

若 Qasper 上也能在严格文档隔离 Test 中产生正向结果，才有更强证据支持“Agent 能根据数据集失败轨迹自主进化 RAG 工具”；若只节省成本而不提准确率，也仍是清晰且可报告的边界结论。

## 十二、建议采用的多工具竞争与回退框架

新数据集上不再固定让 Agent 只生成一个工具，也不应把所有问题强制交给新工具。建议流程为：

```text
Train Baseline 轨迹
→ Analyzer 提出最多 3 个不同故障层级的 ToolSpec
→ Repair Agent 分别生成工具、调用条件和可证伪测试
→ 静态检查与单元测试
→ Dev 上分别与 No-tool Baseline 成对比较
→ Selector 学习“何时调用哪个工具、何时不调用”
→ 低置信度或工具无新增 Evidence 时回退 Baseline
→ 重复搜索达到预算时强制停止或切换工具
→ 冻结工具集合、Selector、回退规则与哈希
→ Test 只运行一次
```

其中 `No-tool Baseline` 也是竞争选项。新工具只有在 Dev 上证明对某类轨迹有净收益时才能被选择；否则自动回退原检索流程。这能避免 FinanceBench 中出现的两种问题：一是单一元数据工具无法修复公式和推理层错误，二是已经找对证据后仍然反复搜索到轮数上限。

评价不能只看答案准确率，还应同时报告：

- 逐工具调用题数及胜/平/负；
- 工具选择准确性或低置信度回退率；
- Evidence Recall / supporting-fact 指标；
- 输入 Token、耗时、轮数和无新增证据的重复调用数；
- Test 上相对同模型 No-tool Baseline 的成对变化。
