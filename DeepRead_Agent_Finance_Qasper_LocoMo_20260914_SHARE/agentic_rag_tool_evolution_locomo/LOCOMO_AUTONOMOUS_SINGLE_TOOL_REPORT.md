# LocoMo 数据集上的自主单工具生成与修复实验报告

**实验日期：2026年9月9日**

## 1. 实验目的

本实验验证一条完整的 Agent 自学习改进 RAG 流程：评测模型先在训练集上运行 DeepRead Baseline，Analyzer 根据错误答案和检索轨迹归纳共性问题，Repair Agent 生成一个数据集适配工具，再利用 Dev 反馈对同一工具进行一次修复，最后将选中的版本冻结并在未参与开发的 Test 上评测。

实验关注以下问题：

1. Agent 能否从训练轨迹中独立提出具有可执行性的工具能力；
2. 工具能否在新对话、新问题上提高回答准确率；
3. Dev 反馈能否改进初版工具；
4. 新工具对输入 Token、输出 Token 和运行时间的影响；
5. 改善与退化分别发生在哪些问题上。

## 2. 数据集与划分

LocoMo 是一个长对话记忆问答数据集。每个样本包含两名人物跨多个日期进行的长期对话，问题涉及事实查找、时间定位、跨会话汇总和人物关系推理。

本实验使用原始数据中的10组对话，构建统一的完整检索库。所有题目均可检索这10组对话，Train、Dev、Test按照目标问题所属的对话进行隔离。

| 数据划分 | 对话数 | 题数 | 用途 |
|---|---:|---:|---|
| Train | 6 | 160 | 运行Baseline，供Analyzer分析并生成初版工具 |
| Dev | 2 | 40 | 评测V1，反馈一次并生成V2，选择最终版本 |
| Test | 2 | 100 | 工具冻结后的最终泛化评测 |

问题采用“对话 × 官方题型”的确定性比例采样。三个集合之间不存在目标对话重叠。完整检索库保持一致，数据库内容未针对某个集合单独调整。

## 3. Baseline配置

### 3.1 模型配置

| 角色 | 模型 |
|---|---|
| Student / RAG答题模型 | `deepseek-v4-flash` |
| Analyzer | `deepseek-v4-flash` |
| Repair Agent | `deepseek-v4-flash` |
| Judge | `deepseek-v4-flash` |
| 向量化模型 | `doubao-embedding-vision` |

所有生成与评测调用的温度均设为0。

### 3.2 DeepRead配置

| 配置项 | 数值 |
|---|---|
| Store | DeepRead |
| 向量检索 | 开启 |
| Hybrid / Semantic检索 | 关闭 |
| `retrieval_topk` | 1 |
| `agent_topk_max` | 1 |
| `max_rounds` | 50 |
| 邻居窗口 | `1,-1` |
| Session pagination | 关闭 |
| Directory structure preload | 关闭 |
| Document title search | 关闭 |
| 并发数 | 1 |
| 索引 | 10组LocoMo对话的共享索引 |

Baseline可以使用DeepRead原有的 `bm25_search`、`regex_search`、`vector_search`、`read_section` 和 `get_doc_structure` 等能力。Baseline未加载自主生成工具，也未附加工具调用策略。

### 3.3 评分方式

Judge根据问题、可接受Gold答案和Student答案给出0—4分：

- 4分：答案完整且正确；
- 3分：核心正确，存在轻微遗漏或不精确；
- 2分：部分正确；
- 1分：大部分内容错误；
- 0分：答案错误、拒答或缺少有效信息。

报告中的归一化准确率计算为：

\[
\text{Accuracy}=\frac{\sum_i \text{score}_i}{4N}
\]

Train160的Baseline归一化准确率为 **86.09%**，平均得分为 **3.444/4**，平均输入Token为 **100,273/题**，平均耗时为 **40.8秒/题**。

## 4. 自主生成工具的过程

### 4.1 Analyzer接收的信息

Analyzer只读取Train数据。输入材料包含18个低分案例和6个满分对照案例，每个案例提供：

- 问题与Gold答案；
- Baseline答案与Judge评分；
- Judge给出的简要评分理由；
- Baseline完整检索轨迹；
- 官方题型。

Analyzer无法访问Dev、Test、历史工具、人工错误标签和已有实验报告。

### 4.2 Analyzer归纳的主要问题

Analyzer将Train错误归纳为四类可重叠的失败机制：

| 失败机制 | 估计案例数 | 主要表现 |
|---|---:|---|
| 摘要级检索遗漏精确事实 | 10 | 检索结果只覆盖会话摘要，颜色、书名、宠物类型、地点等具体答案未被检出 |
| 多会话列表汇总不完整 | 6 | 模型找到部分项目后提前停止，遗漏其他日期中的答案项 |
| 日期与时间顺序错误 | 4 | 相对日期计算、事件先后关系和目标会话定位出现偏差 |
| 人物与说话者归因错误 | 2 | 多人物对话中发生事实错配或代词指代混淆 |

最集中的现象是“检索到了相关话题，未检索到包含答案的具体话语”。Baseline随后进行多轮BM25、正则和向量检索，仍可能依据相近主题生成答案或判断信息缺失。

### 4.3 Analyzer提出的候选工具方向

Analyzer提出了三个候选能力方向：

| 候选能力 | 核心功能 | 预期覆盖问题 |
|---|---|---|
| `utterance_text_concordance_search` | 直接检索逐条对话原文，返回人物、日期、会话编号及上下文 | 精确事实遗漏、人物归因、部分时间问题 |
| `entity_profile_fact_extractor` | 围绕指定人物跨会话汇总事实卡片 | 列表补全、人物属性汇总、归因错误 |
| `session_timeline_builder` | 按日期构建人物或事件时间线 | 日期定位、事件排序、相对时间推理 |

Analyzer最终选择 **`utterance_text_concordance_search`**。选择依据为：摘要级检索遗漏精确事实在Train低分案例中覆盖范围最大；逐条话语检索可以直接利用当前运行环境已经具备的说话者、日期、会话编号和原文信息；该能力同时可为列表汇总和时间推理提供更细粒度的证据。

### 4.4 初版工具V1

Repair Agent依据Analyzer输出生成V1。V1的主要算法步骤如下：

1. 将10组对话展开为6,154个摘要或话语单元；
2. 从问题中识别人名、会话编号和日期条件；
3. 使用条件过滤候选话语；严格条件无结果时逐步放宽过滤；
4. 根据问题词与话语词的IDF加权重合度计算分数；
5. 对引号短语和整句匹配增加权重；
6. 返回带有 `speaker`、`session_index`、`date_time`、`dia_id` 和原文的Top-k结果。

对应的AI生成调用策略要求Student在摘要检索缺少具体值、列表题、日期题和人物归因题中调用工具；最多允许两次查询改写；在放宽条件后仍没有结果时才给出信息缺失结论。

### 4.5 Dev反馈与V2修复

V1在Dev40上运行后，Repair Agent获得Baseline/V1的成对答案、评分、检索轨迹和Gold答案，并对同一能力进行一次修复。修复重点包括：

- 将说话者身份匹配从全局IDF中分离，避免高频人物姓名因IDF较低而受到惩罚；
- 增加轻量词形归一化，提升 `run/running`、`volunteer/volunteering` 等表达的匹配能力；
- 根据初始命中结果进行受限的伪相关反馈，扩展最多12个共现词；
- 加入同一Session内的邻近话语作为 `context_text`；
- 多人物问题采用分人物交替选择，保留轮转次序作为同分决胜条件；
- 保留人物、日期、Session过滤的逐级回退机制。

V2通过静态安全检查和 **11/11** 项冻结合成测试。安全检查期间曾出现嵌套辅助函数被识别为模块公共函数的验证器问题；Harness随后将公共接口检查范围修正为模块级函数，AI生成的工具算法未进行人工修改。

## 5. Dev两轮结果

### 5.1 总体结果

| 方案 | 准确率 | 平均得分 | 胜/平/负（相对Baseline） | 净分 | 输入Token/题 | 输出Token/题 | 耗时/题 | Recall |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| Baseline | 87.50% | 3.500 | — | — | 66,279 | 1,815 | 31.1秒 | 86.88% |
| V1：Train生成工具 | 91.25% | 3.650 | 5/32/3 | +6 | 58,013 | 2,013 | 33.7秒 | 95.00% |
| V2：Dev修复工具 | **91.88%** | **3.675** | 5/31/4 | **+7** | 74,518 | 2,172 | 41.9秒 | 89.38% |

V1相对Baseline提高 **3.75个百分点**，输入Token下降 **12.47%**。V1包含1道−3分的严重退化案例，因此初始诊断门槛标记为FAIL，随后进入修复阶段。

V2相对Baseline提高 **4.38个百分点**，净分从V1的+6提高至+7，并消除了−3/−4分的严重退化。V2出现4道轻度退化，平均输入Token较Baseline增加 **12.43%**。按照预先设定的选择顺序“Dev净分、严重退化数、负例数、输入Token”，最终选择V2进入Test。

Dev反馈带来的准确率增量为 **0.63个百分点**。该阶段说明修复降低了单题严重退化风险，同时带来了更长上下文和更高运行成本。

### 5.2 Dev修复案例：共同志愿活动

**问题：** What type of volunteering have John and Maria both done?  
**Gold：** Volunteering at a homeless shelter

| 方案 | 得分 | 回答表现 |
|---|---:|---|
| Baseline | 4 | 正确识别两人都参与过无家可归者收容所志愿服务 |
| V1 | 1 | 找到了Maria在收容所的经历，也找到了John的多种公益活动，最终概括为宽泛的“社区活动型志愿服务” |
| V2 | 4 | 分别定位Maria长期在收容所服务，以及John在收容所发放食物和物资的记录，恢复Gold答案 |

该案例对应V2的说话者独立计分和多人物证据交替选择设计。修复后的工具能够让两名人物的证据同时进入候选上下文，避免被单个人物的大量相关记录覆盖。

## 7. Test典型案例

### 7.1 精确事实检索：鸟的种类（0→4）

**问题：** Which specific type of bird mesmerizes Andrew?  
**Gold：** Eagles

Baseline首先用BM25检索“bird mesmerizes Andrew”，命中了Session 20中大量关于观鸟和自然的内容。随后又检索到Audrey与蜂鸟的经历，最终回答“hummingbird”，得0分。该题共消耗243,234输入Token，耗时91.9秒。

V2首先调用逐话语工具。工具返回Andrew在Session 1中的原话上下文：

> “Eagles have always mesmerized me; they're so strong and graceful!”

Student据此回答“eagles”，得4分。该题输入Token降至9,980，耗时降至6.0秒。该案例展示了细粒度原文检索对主题相近事实冲突的处理能力。

### 7.2 控制答案范围：下一年度项目（2→4）

**问题：** What projects is Jolene planning for next year?  
**Gold：** 发展可再生能源；为缺乏清洁水源的人提供供水方案

Baseline找到了两项Gold内容，同时加入了更早对话中的STEM志愿项目和绿色技术倡议。Judge将其判为部分正确，得2分。输入Token为344,949，耗时159.6秒。

V2将证据集中到Session 22，提取出Jolene明确列举的两个未来项目，并将其他个人计划与项目目标分开，得4分。输入Token降至60,293，耗时34.4秒。

该案例说明逐话语检索还可以帮助Student控制答案边界，减少跨Session信息混合。

### 7.3 人物与宠物归属：Jolene的宠物（2→4）

**问题：** What pets does Jolene have?  
**Gold：** snakes

Baseline正确提到蛇，也把“Susie”作为类型不明的额外宠物列出，得2分。V2结合多条逐话语证据确认Susie和Seraphim均为Jolene的蛇，同时将Max和Luna归属到Deborah，得4分。输入Token从106,236下降到57,847，耗时从83.7秒下降到24.1秒。

该案例体现了说话者信息、同Session上下文和跨话语汇总的联合价值。

### 7.4 列表覆盖不足：给Deborah带来平静的地点（4→2）

**问题：** What places give Deborah peace?  
**Gold：** 母亲家窗边、海滩、Bali、附近公园的森林小径

Baseline覆盖了全部Gold地点，得4分。V2回答了森林小径、海滩、母亲家和水边地点，遗漏Bali，得2分。该案例显示Top-k逐话语检索在跨多个远距离Session的长列表题上仍可能产生覆盖缺口。

### 7.5 查询扩展引入额外项：Jolene最喜欢的书（4→3）

**问题：** What are Jolene's favorite books?  
**Gold：** *Sapiens*；*Avalanche* by Neal Stephenson

Baseline准确给出两本书，得4分。V2给出两本Gold书籍，同时加入了未命名的“self-discovery book”，得3分。该题的工具初始结果受到“favorite game”等相邻兴趣话题影响，后续广泛检索引入了额外内容。该题输入Token从26,045增加到124,100。

该案例表明伪相关扩展与邻近上下文能够提高召回，也可能扩大答案范围。列表题仍需要更严格的证据资格判断。

## 8. Token减少原因分析

Test平均输入Token从81,832降至53,544，下降34.57%。结合具有完整调用日志的89道题，主要原因可以归纳为以下三点。

### 8.1 检索调用次数减少

| 指标（89道日志完整题） | Baseline | V2工具 | 变化 |
|---|---:|---:|---:|
| 总工具调用数 | 1,060 | 663 | −37.45% |
| 平均工具调用/题 | 11.91 | 7.45 | −37.45% |
| 平均LLM响应轮数/题 | 6.96 | 4.99 | −28.28% |

细分调用数量如下：

| 工具 | Baseline | V2工具 |
|---|---:|---:|
| BM25 | 355 | 133 |
| Regex | 316 | 131 |
| Vector | 57 | 26 |
| Read section | 224 | 114 |
| Get structure | 108 | 89 |
| 自主生成逐话语工具 | 0 | 170 |

新增工具承担了部分精确事实定位任务，使BM25、Regex、Vector和整段读取的重复调用明显减少。

### 8.2 更早获得可作答证据

Baseline面对具体事实时经常先获得主题相关摘要，再通过多次关键词改写继续搜索。V2可以返回带人物、日期和Session的原话，Student更早形成满足回答条件的证据。例如“Andrew着迷的鸟”一题，V2用一次逐话语调用获得包含“Eagles”的上下文，输入Token下降约95.9%。

### 8.3 回答文本缩短

Test平均输出Token从1,976降至1,625，下降17.77%。证据定位更明确后，Student减少了搜索失败说明、候选答案讨论和长篇排除过程。

Token收益具有题目差异。跨Session长列表和查询扩展题仍可能引入更多上下文，“Jolene最喜欢的书”就是输入Token增加的案例。Dev中的V2平均输入Token也高于V1，说明该工具的效率收益依赖问题类型与目标证据分布。

## 9. 实验结论

本实验完成了“Train错误分析—候选能力提出—单工具实现—Dev反馈修复—版本选择—冻结Test”的完整闭环。

在LocoMo冻结Test100上，AI自主生成并修复的逐话语检索工具取得以下结果：

- 准确率从86.75%提高到90.00%，提升3.25个百分点；
- 12题改善、5题退化，净增13分；
- 平均输入Token下降34.57%；
- 平均输出Token下降17.77%；
- 平均耗时下降36.60%。

结果支持“从错误轨迹中自主发现检索粒度缺陷，并生成可执行工具改进RAG”这一技术路线。改善主要来自精确事实定位、人物归属确认和答案范围控制。当前风险集中在跨Session长列表覆盖、查询扩展噪声、相对日期推理和高覆盖调用策略。

Dev反馈将净分从+6提高到+7，并消除了严重单题退化；其增量有限，运行成本有所增加。当前Test仅评测了Dev选中的V2，因此Test总体提升可以归因于“自主生成、Dev修复并选择后的完整流程”，V1与V2各自对Test提升的贡献仍需通过独立消融实验区分。

此外，本实验使用单次对话隔离划分，Test包含2组对话。后续可在保持工具和流程冻结的条件下增加新的对话划分，以评估结果对样本划分的稳定性。
